# THE FINALS Battle Simulator

A browser-based combat simulation tool for comparing weapons from **THE FINALS**.  
The simulator lets users select two contestants, choose weapons, adjust accuracy/headshot settings, change distance and movement rules, then run either a visual one-on-one simulation or a larger statistical analysis.

The project includes a canvas-based battle playback system, multi-run simulation stats, weapon data loaded from JSON, a cross-analysis engine powered by Web Workers, and a heatmap view for comparing matchups across multiple distances and aim profiles.

---

## Features

### Home Menu and Navigation

The app opens on a main menu instead of dropping straight into the simulation. From there:

- **Help** — how the tick-based model works, a stats glossary, and the model's known limits.
- **Weapon / Gadget Stats** — a searchable, sortable table of the raw weapon data plus derived DPS and ideal TTK per class. (Gadget data is not in the dataset yet.) Weapon names link to that weapon's history.
- **Simulation** — the 1v1 visual duel.
- **Meta Simulation** — the cross-analysis run and its matchup heatmap.

---

### Weapon Data Version

Every screen runs on a selectable data version. The **Data** picker in the header (mirrored in the Simulation and Meta Simulation sidebars) rebuilds the weapon roster from `csv/cleaned/weapon_timeline.json`, so the stats table, the 1v1 duel and the cross analysis all move together. It defaults to the newest sheet ingested and remembers the choice.

The hierarchy is enforced in code, not by hand-ordering:

- **Chronology** comes from parsing the version numbers, so a newly added sheet sorts into place on its own (`compareVersions` in both the ingest tool and the UI).
- **A sheet's blanks are its own.** A stat left empty in a row the author did populate means "not applicable" and is never back-filled — this is what keeps a stray `magazine_size: 1` in the 5.8 sheet from making the Dagger reload after every swing.
- **A weapon listed with no stats at all** is a coverage gap, and inherits the last version that recorded it. That is what keeps melee weapons playable at 11.3.0, and each one is labelled with where its numbers came from.
- **Reach limits** (melee swing range, the flamethrower's cone) are engine knowledge no sheet records, held in `tools/weapon_aliases.json` under `runtime_defaults` and applied only where the selected sheet is silent.

Materialising 10.0.0 reproduces the bundled `weapons_s10_cleaned.json` field for field, apart from Dual Blades and Spear, whose damage the bundled file leaves as text and which instead carry a usable number forward from an earlier sheet.

### Weapon History

Clicking a weapon opens its history across seven community data sheets (1.5 → 11.3.0, CSV and XLSX):

- a chart of any metric over time — damage per shot, sustained DPS, ideal TTK per class, shots to kill, RPM, magazine, reloads, dropoff — with dashed segments where a sheet did not cover that weapon;
- a wiki-style snapshot of the weapon at any single version, including derived TTK/STK, the source sheet's author, and that sheet's caveats;
- a change log of every difference between consecutive versions, coloured by whether it helped or hurt the weapon and tagged with confidence.

Data comes from `csv/cleaned/weapon_timeline.json`, generated by `tools/ingest_weapon_history.mjs`. See `csv/cleaned/README.md` for the trust model, tolerances and validation.

### Multi-Run Simulation

The simulator can run repeated simulations to estimate matchup consistency.

Multi-run output includes:

- Player 1 wins
- Player 2 wins
- Ties
- Average time to kill
- Average HP remaining
- Average bullets to kill
- Win-rate distribution

This helps reduce the randomness of single simulations and gives a better sense of how favorable a matchup is.

### Cross Analysis (Meta Simulation)

The cross-analysis system compares one selected attacker against every other weapon across several distances and aim profiles. It is driven from the Meta Simulation screen, which owns its own weapon/accuracy controls, a runs-per-scenario setting (1K / 10K / 50K), a live scenario count, and a cancel button that terminates the worker pool mid-run.

**Solved, not sampled.** Every matchup in the grid is resolved by `duel_solver.js`, which computes the exact probability of each outcome instead of running duels and counting winners. The full 1,260-scenario grid completes in about half a second, carries no sampling error, and is bit-for-bit reproducible.

A **Method** control offers `Exact` (default) or `Sampled`, and sampling restores the runs-per-scenario choice (1K / 10K / 50K). Sampling exists to cross-check the solver against the engine it replaced — it is seeded, so a sampled table is also reproducible. Comparing the two across all 1,260 cells is what surfaced the tick artefact below.

The solver works because neither fighter reacts to damage: shot timing is fully deterministic and only the hit rolls are random, so each fighter's kill-time distribution can be solved independently and then compared. With damage fixed per shot, "damage dealt so far" collapses to two counts (body hits, head hits) — a few hundred DP states rather than an exponential tree. `simulate.js` remains for animated playback and as the sampling fallback for duels where fighters move; its rolls now go through a seeded generator so any run can be replayed.

Two outcomes are reported more honestly than before: a 60-second stalemate is a **timeout** rather than a win awarded on remaining health, and a **tie** means the killing blows actually coincide rather than landing in the same 10 ms tick.

That second point was not cosmetic. Comparing the exact and sampled grids cell by cell, 89 of 1,260 cells disagreed by more than three standard errors — all of them cells where the tick invented ties out of near-simultaneous kills, taking them mostly from the attacker's wins. The worst case shifted a win rate by **5.2 percentage points**. Shrinking the tick to 2 ms makes the phantom ties vanish and the sampled numbers converge on the solver's, which is the evidence that the solver is right and the tick was wrong; `tools/test_solver.mjs` pins that as a regression test.

**Stand and fight.** The meta grid holds both duellists at the listed range for the whole fight — no advancing, no closing the gap, no class-speed advantage — so each cell isolates the weapon's performance at that range. Melee weapons can only land hits at ranges inside their own reach and lose outright everywhere else. Movement is not configurable here; the 1v1 Simulation screen still models it.

The current cross-analysis setup uses:

- Multiple Web Workers
- A shared job queue
- Work stealing
- Progress tracking
- Profiling logs
- Final result rendering

Each job runs many simulations and returns:

- Defender weapon
- Defender class
- Distance
- Aim profile
- Wins
- Losses
- Ties
- Win rate
- Average attacker TTK
- Average defender TTK
- Favorability result

Favorability is grouped as:

- Favorable
- Even
- Unfavorable

### Heatmap View

The heatmap turns cross-analysis results into a visual matchup table.

Each cell shows:

- Win rate
- Average attacker TTK
- Average defender TTK
- Tooltip breakdown by aim profile
- Color-coded matchup favorability

The heatmap can help quickly identify which matchups are strong, weak, or highly distance-dependent.
